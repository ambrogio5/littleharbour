## Rendering decision

Use **SwiftUI + SpriteKit**, with a small `SKView` representable for camera gestures. SwiftUI handles adaptive sheets/inspector, Dynamic Type, native buttons, lists and dialogs, accessibility, document import and sharing. SpriteKit handles GPU-rendered independent textured layers, depth ordering and touch coordinates. This fits an authored 2.5D map with tens of sites; custom Metal would add substantial rendering/resource/lifecycle code without measured evidence of a benefit. Pure SwiftUI Canvas would require more custom hit testing/camera infrastructure and would not provide the same scene graph. A full SceneKit/RealityKit 3D conversion would require an entirely different model/lighting asset pipeline and would not preserve the approved composition.

SpriteKit integrates with SwiftUI and provides Apple's 2D rendering framework: [SpriteKit](https://developer.apple.com/documentation/spritekit), [SpriteView](https://developer.apple.com/documentation/spritekit/spriteview). We use SKView directly to control gesture recognition and lifecycle precisely. No custom Metal shader or claim of measured physical GPU performance is made.

The authoritative simulation remains **JavaScript**, executed locally by Apple's [JavaScriptCore](https://developer.apple.com/documentation/javascriptcore). This is deliberately not described as a Swift rewrite. Reusing it preserves the actual economy, action validation, captured paid voyage rewards, queue durations, save migration and all existing tests. Swift decodes typed presentation snapshots and invokes an allowlisted action identifier; it never evaluates imported save data as executable code. No remote scripts or browser runtime are used.

`native/bridge.js` creates descriptors by trying original engine actions on detached copies. Actual actions look up a fresh descriptor, mutate a transaction copy, validate it with `parseSave`, then publish the town and evolution together. Stale construction, stage and order identifiers cannot spend twice. Reservations and project plans reuse the original engine. Tick uses the original simulation, including its intentional pause/no-offline semantics.

`EngineRuntime` confines JavaScriptCore to the main actor and checks exceptions at each call. `GameStore` owns lifecycle, snapshots and saving. `SaveRepository` is a narrow filesystem boundary with atomic writes, verified backups and unexpected-write detection. CPU work remains on the main actor at this scene size; physical profiling may justify moving the runtime to a dedicated actor later.

## Graphics pipeline

The native v0.2 pass replaces the initial SVG exports with **painted raster terrain and transparent architecture** made with the built-in ImageGen tool. The source atlases, exact prompts, stable-frame extraction/packing script and hashes are committed under `native/art-source/painted-v2`. The initial source remains available in git history; browser art is unchanged. See [asset provenance and state reuse](../art-source/painted-v2/README.md).

The 120 named textures are 24 kinds × five variants, plus a painted olive tree and an opaque native icon. There are 24 distinct completed object designs. Three families provide empty plots/construction; ordinary upgrades use painted annexes, while upgraded houses and boats have separate silhouettes. Not every variant corresponds to an economic state; unused ripe variants intentionally reuse built pixels. Wheat visibly changes from green to gold. The world still selects individual SpriteKit nodes from actual saved state, never a baked town screenshot.

Four fixed coastal landmarks receive native presentation anchors matching the new shoreline. This does not change saved neighbourhood plots or source economy coordinates. Selection/labels follow rendered boat positions. Backed labels hide on distant zoom; players can toggle ordinary labels. Working bakery/kiln smoke and harvest pulses stop for pause/Reduce Motion. Full worker/wheel/wake animation remains future work.

A single terrain texture is about 19 MB decoded (1800×2700×4), before GPU overhead. Each 384×384 sprite is about 0.56 MB decoded. Textures are cached on demand with a 48 MB SpriteKit cache cost limit and a separate 12 MB UI-image cache limit. These are cache policies, not measured total process-memory limits; live nodes retain their textures. Render rate is capped at 30 FPS; the economic interface refreshes at most twice per second. No physical memory, thermal, battery, frame-rate or oldest-device budget is certified yet. Atlas packing, texture compression and terrain tiling should follow real profiling, not a speculative engine replacement.

## Accessibility and interaction

Native text uses semantic font sizes; management content scrolls. Controls provide named labels, disabled-state explanations and generally at least 44-point touch areas. Explore and Sites provide alternatives to pan, pinch and tiny world objects. VoiceOver receives action-result announcements. Reduce Motion suppresses moving voyage sprites, smoke and harvest pulses. The app uses a consistent daylight palette. Compact HUD/navigation typography caps at XXXL to preserve controls; management text remains uncapped and scrollable. At accessibility sizes, inventory summaries become vertical and map controls use named icons. The AX5 simulator test harvests and reaches Settings; this is a smoke check, not a full accessibility audit. Map labels are decorative; the searchable Sites directory is the authoritative accessible building list. Full VoiceOver, Switch Control, contrast and extreme Dynamic Type audits on devices remain release work.

## UI state and preferences

Site selection routes built artisan/inland sites to production and filters by structured engine action arguments. The boatyard is distinguished from numbered fleet boats. Category navigation clears stale site context, filters/search reset on destination changes, and the inspector returns to its top. iPhone sheets use their full available height; wider windows keep the management panel beside the map. Feedback occupies safe layout space instead of intercepting controls.

`mapLabels` and `hapticFeedback` are local UserDefaults preferences; they do not alter town saves. The privacy manifest declares app-only preference access with `CA92.1`, in addition to the existing monotonic-time reason. See Apple's [required-reason API documentation](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype). No tracking or collected-data declaration was introduced.
